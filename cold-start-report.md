# Холодный старт Chrono: разбор и правки

Ветка `worktree-agent-a5d38f1e77d0572df` от `feature/daily-schedule` (`3fabf73`). Эмулятор `emulator-5554` (Android 16, x86_64, 4 ядра, **2 ГБ ОЗУ, 1,2 ГБ уже в swap**). Release собирался `dotnet publish -c Release -f net11.0-android`, подпись `debug.keystore`. Все вызовы adb шли с `-s emulator-5554`, телефон пользователя не трогался.

## Главное

- Старт на эмуляторе в основном определяют рантайм и нехватка памяти, а не код приложения. На Redmi K70 Pro первый запуск после установки занимает 1,3 с, поэтому цифры эмулятора нельзя переносить на телефон один к одному.
- Однако у приложения есть работа на главном потоке до первого кадра, и она тоже уходит в ANR «failed to complete startup». Эту часть уменьшено, всё без изменения логики постановки будильников.
- 10–15 с из приёмки Google-синхронизации воспроизвелись только сразу после установки (первый `am start` после `adb install`): 12,6 с и 15,0 с. Устойчивый холодный старт Release в моих замерах 3,1–7,2 с, медиана около 4,3 с.

## Таблица «до / после»

Release, `am start -W -S`, `TotalTime`, медиана из 5. Два чередующихся раунда (база и итог по очереди), потому что эмулятор «плывёт» от прогона к прогону.

| после (`41d2552`), медиана TotalTime | 3916 мс | 3953 мс | 3934 мс |

Выигрыш около 0,4 с (≈9 %) на устойчивом старте и около 0,8 с на первом запуске после установки. Разброс отдельных прогонов (3,1–7,2 с) больше самого выигрыша, поэтому по каждой правке ниже приведены не только `TotalTime`, но и внутренние метки.

## Разбивка времени старта

Метки `ChronoStart` (мс от строки «Start proc»), медианы 5 холодных запусков Release. «До» — база с метками; «после» — сборка после правок 1–3 в «тихом» состоянии эмулятора (абсолютные значения сопоставимы приблизительно, надёжнее сравнивать длительности фаз).

| Фаза | до | после |
|---|---|---|
| форк процесса до загрузки libmonodroid | 354 | 191 |
| старт рантайма до `Application.OnCreate` | 1011 | 851 |
| `CreateMauiApp` (DI, шрифты регистрируются лениво) | 235 | 350 |
| разрешение `App` в DI до тела конструктора | 145 | 38 |
| `RescheduleAll` в конструкторе `App` | 770 | 525 |
| **весь `Application.OnCreate`** | **1230** | **982** |
| `MainActivity.OnCreate` до `CreateWindow` | 290 | 250 |
| `CreateWindow` | 153 | 103 |
| первый кадр (`Displayed`) | 3837 | 3221 |
| от показа splash до `Shell` выставлен | 2289 | 2287 (до сокращения анимации) |
| список показан (`AlarmListPage.OnAppearing`) | 5132 | 4615 |

Внутри `RescheduleAll` (первый вызов, эмулятор): чтение и разбор alarms.json 320–340 мс на отражении, `TimeZoneInfo.Local` (разбор tzdata) 110–250 мс, `Preferences` и разбор реестра таймеров 50–100 мс, цикл `AlarmManager` 130–200 мс (первые JNI-вызовы). Второй вызов `RescheduleAll` из `BootReceiver` (его присылает WorkManager при старте процесса) занимает уже ≈40 мс.

После показа splash: анимация (по коду 810 мс покачивания + пауза 250 мс = 1,06 с), создание `AppShell` ≈215 мс, выставление страницы ≈230 мс, первый `OnAppearing` списка ≈115 мс. Вкладки уже ленивые (`ContentTemplate`), создаётся только «Будильники».

## Три главные причины

1. **Рантайм и память эмулятора** (специфично для эмулятора). Старт CoreCLR идёт 0,65–1,0 с, а сразу после установки 2,4–3,5 с: 2 ГБ ОЗУ при 1,2 ГБ swap, в дампе ANR 21 000 major faults и 16 % iowait, главный поток внутри `libclrjit.so`. Release уже собирается с trimming и композитным частичным ReadyToRun (`PublishReadyToRun`, `--partial` с MAUI mibc), то есть включено всё, что нужно. Проверено: полный R2R (`MauiEnableFullReadyToRun`) не дал выигрыша и добавляет 14 МБ.
2. **Работа главного потока в `Application.OnCreate` до первого кадра**: `CreateMauiApp`, разрешение `SyncLauncher` (`CalendarSync`, `GoogleCalendarClient`, `HttpClient`) и `RescheduleAll` с первым в процессе разбором JSON на отражении и инициализацией часового пояса. Это общая часть для любого холодного старта, в том числе процесса, поднятого приёмником будильника или `BootReceiver`.
3. **Путь от splash до списка**: анимация 1,06 с, создание `AppShell`, выставление страницы и первый `OnAppearing`. На телефоне с первым кадром за ≈1,3 с анимация — самая крупная управляемая часть пути до списка.

## ANR «failed to complete startup»

- Механизм: диспетчер активностей ждёт, пока процесс завершит `bindApplication`, то есть `Application.OnCreate`. В нём MAUI создаёт `App` и выполняет `RescheduleAll`. Не уложились — ANR, процесс убит.
- Воспроизведено в этом сеансе: Debug-APK (150 МБ, `EmbedAssembliesIntoApk`) после `adb install -r`; процесс поднят `BootReceiver` (`MY_PACKAGE_REPLACED`), через ≈20 с «ANR in com.chrono.alarm … failed to complete startup», 20 977 major faults. Приложение запущено повторно, всё работает.
- В прежнем дампе (`15:29`, `Debug Store … BindApp`) главный поток стоял в JIT. Release с R2R в моих замерах не попадал в ANR: `Application.OnCreate` заканчивался на 2,0–6,1 с.
- Всё, что уменьшает `Application.OnCreate`, уменьшает риск этого ANR (по дампу ANR; не доказано, что на телефоне он когда-либо возникает).

Связь с D2 (сигнал звонит, `RingPage` не показан): процесс, поднятый `AlarmReceiver`, проходит тот же `Application.OnCreate`, прежде чем `AlarmRingService` вызовет `StartForeground`; затем экран сигнала ждёт `AppShell` и `AlarmListPage.OnAppearing` (`RingLauncher.ShowPendingAsync`). Звук идёт из сервиса и от UI не зависит. Медленный старт расширяет окно D2, но причиной «звонит без экрана» сам по себе, по этим замерам, не оказался. `RingLauncher` и показ `RingPage` не менялись.

## Что не сделано и почему

- **`RescheduleAll` не откладывался** (ограничение брифа). Сделан быстрее, но по-прежнему выполняется синхронно в конструкторе `App`. Отложить его (например, на первый кадр) дало бы ещё ≈0,5 с, но оставило бы окно, где после перезапуска/обновления будильник не стоит.
- `RingLauncher`, `RingPage`, `BootReceiver`, `AlarmRingService` не менялись.
- Полный R2R: нет выигрыша. Mono вместо CoreCLR (`UseMonoRuntime`) и `TrimMode=full` не пробовались: слишком крупная смена для «безопасных правок».
- Создание `AppShell` во время анимации splash сэкономило бы 30–200 мс (зависит от устройства), но внесло бы подвисание в анимацию и трогает область D1; описано, не сделано.
- Автоинициализация WorkManager в `Application.OnCreate` (≈130 мс на главном потоке) не отключалась: `SyncWorker` её использует.
- Правки только под эмулятор (подбор памяти, swap, режимы ART) не делались.

## Замер на телефоне (выполняет пользователь)

Release-APK с метками (подпись `debug.keystore`), 5 холодных запусков:

```
dotnet publish src/Chrono/Chrono.csproj -c Release -f net11.0-android -p:ChronoStartTrace=true -p:AndroidKeyStore=true -p:AndroidSigningKeyStore="%LOCALAPPDATA%\Xamarin\Mono for Android\debug.keystore" -p:AndroidSigningKeyAlias=androiddebugkey -p:AndroidSigningKeyPass=android -p:AndroidSigningStorePass=android -o <каталог>
adb -s <серийный номер телефона> install -r <каталог>\com.chrono.alarm-Signed.apk
adb -s <серийный номер> logcat -c
adb -s <серийный номер> shell am start -W -S -n com.chrono.alarm/crc64fd681c359b5f5c68.MainActivity
adb -s <серийный номер> logcat -d -v time | findstr "ChronoStart Start.proc Displayed"
```

Фазы читаются по меткам: `Application.OnCreate` (конец минус «Start proc») — ANR-критичная часть; `SplashPage: показана` → `SplashPage: Shell выставлен` → `AlarmListPage: показана` — путь от splash до списка.

## Методика

Скрипты замера: `%TEMP%\csx\meas.py` (установка, первый запуск после установки, N холодных запусков с `-S`, парсинг logcat), сборка `%TEMP%\csx\build.ps1`. После изменения свойств сборки нужна очистка `obj`/`bin`: свойства не входят в Inputs инкрементальных целей, без очистки R2R не пересобирается.
