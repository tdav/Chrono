## D1. Падение `FragmentManager is already executing transactions` — исправлен

**Корневая причина — не `OnNewIntent`/`RingLauncher`, а смена страницы окна во время остановки активити.**
`SplashPage.OnAppearing` через ≈1,5 с делает `Window.Page = AppShell`. Если экран выключили, пока шёл splash (активити остановлена, `FragmentManager.IsStateSaved`), MAUI (`FragmentManagerExtensions.RunOrWaitForResume`) откладывает транзакции фрагментов нового Shell до возобновления и выполняет их из `FragmentLifecycleCallbacks.OnFragmentResumed` — то есть внутри `onPostResume → dispatchResume`. Там идёт вложенный `commitNow`, и процесс падает.
Сигнал здесь ни при чём: падает и без него.

Доказательство (до правки):
- Воспроизведение без сигнала: `force-stop`, запуск, выключить экран через 3 с (`keyevent 223`), через 15 с включить экран — `FATAL EXCEPTION` 2 раза из 2 (w1, w2).
- Со сигналом: запись `Ring` на +60 с, запуск, экран выключен через 3 / 1 / 6 с — падение в 4 из 5 прогонов (c1, c3, c4, c5; c2 прошёл).
- logcat (`fix-A2-d1-before-logcat.txt`): `Unable to resume activity ... IllegalStateException: FragmentManager is already executing transactions` ← `FragmentManagerExtensions_CallBacks.onFragmentResumed` ← `FragmentStateManager.resume` ← `FragmentManager.dispatchResume` ← `FragmentActivity.onPostResume` ← `MauiAppCompatActivity.onPostResume`.
- Проверка гипотезы «навигация из `OnAppearing`/`OnNewIntent`»: добавил `Task.Yield` в `AppearingAsync` (подсказка из коммита 1c8aed4) — падения остались (c3–c5). Значит, не она. Правку откатил, в коммит она не вошла.
- Дефект есть и на `main` (`SplashPage` там тот же), не регрессия ветки; на `main` приёмка его просто не поймала.

Исправление (`Views/SplashPage.cs`, только Android): перед `Window.Page = AppShell` ждать `Lifecycle.CurrentState >= Resumed` (опрос 100 мс). Продолжение после `Task.Delay` приходит отдельным сообщением главного цикла, то есть после `onPostResume`.

После правки:
- Без сигнала: выключить через 3 / 1 / 6 с, включить — 0 падений (w3 упёрся в ANR после свежей установки, w4, w5 чистые).
- Со сигналом, тот же сценарий, экран выключен через 3 / 1 / 6 с (d1–d3), и ещё раз на финальной сборке (f3, f1, f6): `RingPage` показан, падений нет, 6 из 6 (`fix-A2-d1-after-ring.png`).

## D2. Экран сигнала не показывается — не воспроизведён, исправлен только общий корень с D1

Правка D1 снимает один из путей (остановленное активити при старте). Своего корня D2 найти не удалось. Прогоны (`RingPage` на экране, падений нет):
- До правок (HEAD ветки): 3 реальных `Ring` при выключенном экране на вкладках Будильники / Распорядок / Настройки (по одному) + 16 доставок intent полноэкранного сигнала (`am start ... --es alarm_id`) при выключенном экране на всех четырёх вкладках (по 4 круга) — 19 из 19.
- После правок: реальный `Ring`, процесс убит `am kill` (холодный старт по сигналу), вкладки 0/1/3 — 3 из 3; процесс жив, приложение в фоне (HOME), вкладки 1 и 0 — 2 из 2; сигнал в момент холодного старта (splash, +0…+6 с) — 28 из 29 (с обеими версиями `AppearingAsync`: с `Task.Yield` и без).
- Единственный сбой (`fix-A2-d2-anomaly-splash.png`, прогон s5-1): `am start` с сигналом через 1 с после запуска, через 25 с на экране всё ещё splash, `RingPage` нет, падения нет. Журнал не сохранился, повторить в 20+ прогонах не удалось. Не исключено, что это замедленный холодный старт (на эмуляторе 8–15 с, ANR-диалог после установки), но исключить влияние опроса `Resumed` из правки D1 полностью я не могу: цикл ждёт только пока активити не возобновилась (экран выключен или поверх неё другая активити), в этих случаях переключение окна и так упало бы.
- Гипотезы без подтверждения: (а) на устройстве приёмки полноэкранный запуск блокировался системой (разрешение `USE_FULL_SCREEN_INTENT` на API 34+ сбрасывается при обновлении, приёмка шла «после обновления»); (б) сбои 10:54 и 11:37 были следствием D1 (процесс перезапущен). Предложение: при следующей приёмке снять `dumpsys` разрешения (`appops get com.chrono.alarm USE_FULL_SCREEN_INTENT`) и `logcat` на момент сбоя.

## D3. Уведомление `Notify` теряется — исправлен

Причина подтверждена: три записи `Notify` на одну минуту, до правки — 1 уведомление из 3 (`N3`), две других потеряны (`ScheduleReceiver` читал `IsEnabled`, а `GetAll` в `RescheduleAll` соседнего приёмника уже выключил сработавшую разовую запись).
Исправление:
- `ScheduleReceiver` больше не проверяет `IsEnabled`: выключенную пользователем запись `Sync` уже снял с `AlarmManager`; сверка `Alert == Notify` и минут напоминания с хранилищем осталась.
- Время срабатывания едет в `PendingIntent` (`at_ticks`, ставится в `AlarmScheduler.Sync` и для начала, и для напоминаний). Без этого у повторяющейся записи `GetAll` уже перенёс `At` на следующий раз, и уведомление показало бы время и день следующего раза (проверено).
- Другие приёмники: `AlarmReceiver` для основного звонка запись не читает; для напоминания читает до `At`, когда запись ещё включена; `SmartWakeService` — до `At`. Тем же дефектом не страдают.
- Правило синхронизации не затронуто: момент выключения/удаления записей (`AlarmService`) не менялся, Delete в Google для разовой «Один раз и удалить» работает как прежде.

После правки (на эмуляторе): три `Notify` на одну минуту — 3 уведомления из 3; повторяющаяся «каждый день» показала время срабатывания (`05:04`), хотя `At` в файле уже `2026-10-22`; напоминание за 5 мин показало `05:09–05:39` (начало и длительность записи).

# Раунд 1 (по ревью `fix-A2-review.md`)

Коммиты: `f429139` (I1, I2, M2 и тест), `bee204b` (M1, I3). Тесты: `dotnet test tests/Chrono.Tests` — 305 зелёных (299 было, 6 новых на `Alarm.IsOccurrence`); сборки Android и iOS — 0 ошибок.

## I1. «Один раз и удалить» без длительности терялась — исправлено
- Подпись и длительность записи теперь едут в extras `PendingIntent` (вместе с временем начала). Если записи в хранилище нет, а таймер основной (не напоминание), приёмник показывает уведомление по extras. Пользовательское удаление (`AlarmService.Delete`, в том числе `fromSync`) всегда вызывает `scheduler.Cancel(id)`, поэтому до приёмника доходит только автоудаление `GetAll`.
- `AlarmService` не менялся: момент удаления и `Delete` в Google те же.
- Проверка на эмуляторе: три `Notify` плюс «Один раз и удалить» без длительности на одну минуту (экран выключен): пришли все 4 уведомления; запись «Один раз и удалить» к этому моменту уже удалена из `alarms.json`.

## I2. Отложенная доставка и `Sync` — исправлено (оба шага)
- **Шаг 2 (ключ с временем).** Data-URI: `chrono://notify/{id}/{ticksAt}` и `…/{ticksAt}/r{минуты}`. Следующее срабатывание повторяющейся записи больше не затирает недоставленный текущий таймер.
- **Шаг 1 (Sync не снимает прошедшее).** `AlarmScheduler` ведёт реестр поставленных таймеров Notify (`Preferences`, ключ `notify_keys`: id записи -> список ключей). `Sync` снимает только те прежние ключи, чей момент срабатывания в будущем и которых нет среди нужных (правка времени или напоминаний, выключение, смена уровня). Прошедшие не трогает. Реестр хранит ключи только записей, которые есть в списке; Sync под замком (его вызывают и главный поток, и фоновая синхронизация).
- **Все места `Cancel` для notify.** `Sync` (основной и напоминания) переписан на реестр; `Cancel(id)` (удаление записи) снимает все ключи записи из реестра, в том числе прошедшие и ждущие доставки. Других вызовов нет (`RingViewModel.Load` вызывает тот же `Cancel(id)` и затем `RescheduleAll`; для звонящей записи реестр Notify пуст). `IAlarmScheduler` и iOS не менялись.
- **Сверка в приёмнике, код без MAUI:** `Alarm.IsOccurrence(at)` = `at == At` или (повторяющаяся и `NextAfter(at - 1 тик) == at`). Приёмник показывает уведомление, только если время из intent — срабатывание текущего правила записи; устаревший ключ после правки времени не показывает ничего.
- **Тесты (6 штук, `AlarmModelTests`):** разовая и «Один раз и удалить» (точное время, время изменено, тот же час другого дня); ежедневная с уже перенесённым `At` (вчерашнее срабатывание ещё действительно, другое время — нет); по дням недели (выбранные дни, дни изменены, без дней = каждый день); ежегодная; до `StartsOn`.
- **Мутация.** `NextAfter(...) == at` заменено на `true` -> 4 красных теста из 6; `at == this.At ||` заменено на `at != this.At &&` -> 3 красных. Код возвращён, `git diff` по `Alarm.cs` — только добавленный метод (6 строк). Замечание: после возврата файла `dotnet test` взял устаревшую сборку (время изменения файла старше сборки) и показал ложные 3 красных; `touch` и повторный прогон — 305 зелёных.
- **Эмулятор, доставка после выхода из Doze.** Модель отложенной доставки: квота `allow_while_idle_quota=1` на час (`device_config`) плюс `dumpsys deviceidle force-idle`: первое уведомление доставляется, остальные откладываются. Между сроком и доставкой вызван `RescheduleAll` реальным путём: `cmd alarm set-time` -> `BootReceiver` (TIME_SET) -> `GetAll` + `Sync`. Затем квота снята, `unforce`, экран включён. Записи: `E1` (+90 с), `E2` разовая, `E3` ежедневная, `E4` «Один раз и удалить» без длительности (все Notify, срок E2–E4 на 10 с позже E1).
  - Сборка `6241877` (до правок), прогон `DC`: до `Sync` доставлена только `DC-E1`; после `Sync` ожидающих таймеров Notify 2 (было 3); после выхода из idle пришла только `DC-E1`. **E2, E3, E4 потеряны.**
  - Эта ветка (`f429139`), прогоны `DR` и `DD`: до `Sync` доставлена только `E1`; после `Sync` ожидающих таймеров 4 (E2, E3 сегодня, E3 завтра, E4); после выхода из idle пришли E1, E2, E3, E4. У E3 в тексте время сегодняшнего срабатывания (`05:55`), хотя `At` в файле уже на завтра; E4 показана по extras, хотя её уже нет в `alarms.json`.

## M2 — исправлено
Приёмник показывает уведомление только если `alarm.IsEnabled || alarm.IsOneShot()`: у повторяющейся записи, выключенной пользователем, уведомления нет, а разовая, выключенная `GetAll` после срабатывания, показывается (это подтверждено прогонами I1 и I2: E2 выключена `GetAll`, уведомление пришло). Отдельной проверкой выключенной повторяющейся записи на эмуляторе не покрыто (нужна гонка `Toggle` и уже ушедшей рассылки); проверено чтением кода.

## M1 — исправлено
Цикл ожидания в `SplashPage` выходит, если состояние жизненного цикла `DESTROYED`, и страницу окну не выставляет. Эмулятор: запуск и «Назад» через 2 и через 4 с — в журнале `splash: активити уничтожена через 1 мс, выходим`, цикл не продолжается (до правки он крутился бы, пока сборщик не освободит активити).

## I3 — диагностика добавлена
Если splash вынужден ждать, `Android.Util.Log` с тегом `Chrono` пишет: вход в ожидание (состояние), каждые 2 с «всё ещё ждём N мс, состояние …», выход (сколько ждали, состояние) и выход по `DESTROYED`. Пример (экран выключен через 1 с после запуска, сигнал через 60 с): `ждём возобновления активити, состояние CREATED` ... `возобновлено через 50846 мс, состояние RESUMED`. Ожидание идёт в состоянии `CREATED`: активити так и не была запущена, пока экран не включил сигнал.
